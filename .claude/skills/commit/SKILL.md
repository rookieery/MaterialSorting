# Git Commit Skill

## 上下文
- 历史参照：!`git log --pretty=format:'%s' -10`（历史信息多为旧版超长风格，只参照其 type 前缀习惯，**不要**模仿其长度与密度）
- 当前状态：!`git status --short`
- 本仓库提交信息惯例（必须遵守）：
  - **单行中文信息，无 body、无 AI 署名脚注**
  - 格式：`<type>: <主题> - <简短说明>`（type 后用半角冒号+空格；改动单一时 `- <说明>` 可省）
  - type 取值：`feat` / `fix` / `docs` / `refactor` / `test` / `chore`
  - **精简为先**：一句话说清这次提交干了什么即可，全行建议 ≤60 字
  - 说明只点核心改动（做了什么事、动了哪块），**不展开**：动机背景链、决策依据、逐文件清单、参数值、测试数字、文档同步明细
  - 多个改动点最多列 2~3 个关键词，用「、」串联；其余细节留在会话与 .docs 里，不进 commit

## 执行步骤

1. **收集证据**：
   - `git status --short` 看全部改动文件；
   - `git diff` + `git diff --cached` 读具体变化（新增文件用 Read 看内容）；
   - 结合**当前会话上下文**——本会话里做了什么、为什么做、用户说过什么要求，这是「关键依据/决策」段的主要来源；diff 只作证据核对，不凭空编造。

2. **生成提交信息**：按上述惯例写单行信息。主题短语概括这次改动（如「编辑画布物理口径统一」），说明补充关键对象或范围（如「manifest 增发 raw_polygon、前端渲染与指标统一切物理轮廓」），点到为止；写完自查超没超过一行 ~60 字，超了就删细节。

3. **暂存并提交**：
   - 若用户在 `/commit` 后附带参数（指定文件、指定主题等），按参数执行；
   - 否则 `git add -A` 暂存全部改动；
   - 提交用 heredoc 防引号转义问题：
     ```bash
     git commit -m "$(cat <<'EOF'
     <提交信息>
     EOF
     )"
     ```

4. **汇报**：提交成功后简洁展示 commit hash + 提交信息；若改动涉及文档同步但本次没同步，提醒可跑 `/sync-docs`。

## 注意事项
- 工作区干净（status 无输出且无未跟踪文件）时不提交，直接告知「没有可提交的改动」。
- **只 commit 不 push**，除非用户明确要求。
- 提交信息必须与 diff 实际内容一致，不凭空编造本会话没做过的改动。
- 临时文件、调试产物若被 `git add -A` 带入且明显不该入库（如本地截图、临时脚本），先向用户确认再决定是否排除。
