## 一、背景与目标

排料 90% 攻坚已验证 hybrid 路线成立（sparrow 算法核 + 自研 v0.3 约束层）；阶段 0–1 实测：erode10+rot 多 seed **max 90.38%**，阶段 1 证明 erode 路径合法、90.38% 是真实利用率。在此基础上提出两个增强想法，合成一个本地可视化工作台。

### 想法 1：求解过程可视化
把 sparrow 求解（单次 / 多 seed）的过程变成可视化——排料图随时间演变，用于直观理解算法行为、给调参提供反馈。

- **原疑虑**：是否需要本地部署 sparrow 源码？
- **验证结论（2026-08-08）：不需要本地部署。** 测试 `spyrrow.ProgressQueue`：求解 15s 推送 **289 个中间报告，每个中间解都带完整 `placed_items`**（含 rotation/translation）。当前 [`sparrow_baseline.py:254`](nesting_engine/sparrow_baseline.py#L254) 的 `solve_with_progress` 只取了 `density`/`width`、**丢弃了排料图**；只要把中间解的 `placed_items` 也存下来，求解每一步的排料图都能渲染。pip 的 spyrrow 完全够用，不碰 sparrow Rust 源码。

### 想法 2：约束可视化配置
把 [排料规则_详细版.md](排料规则_详细版.md) 的 v0.3 约束（旋转公差、重合上限、erode 深度等）做成可调界面，自己调参实时看不同搭配的排料效果，摸参数手感。

### 合成目标
一个 **localhost 排料可视化工作台**：左 = v0.3 参数面板（可调）｜中/右 = 排料图 SVG（实时/回放）｜底部 = 求解过程回放控制 + 收敛曲线。

## 四、技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | **FastAPI + uvicorn** | 与 sparrow 同为 Python；WebSocket 原生支持；轻量、启动快 |
| 前端 | **原生 HTML + JS + SVG** | 自用，不引前端框架，零构建、好改 |
| 通信 | **WebSocket** | 实时推求解中间解（高频，适合推流） |
| 依赖 | `pip install fastapi uvicorn` | 仅此两项；前端零依赖 |

> 前端不引框架是当前决策（自用、轻）。若后续要给版师/客户演示再评估 Vue/React。

## 五、架构与数据流

```
浏览器  localhost:8000
    ↑  WebSocket JSON: {elapsed, phase, density, width_mm, placed_items[{id,rotation,translation}]}
    |
FastAPI  server.py
    ↑  回调 on_report(中间解)
    |
solver.py  （子线程求解）
    ↑  ProgressQueue.drain() → 中间 sol（含 placed_items）
    |
sparrow  （spyrrow pip，不改源码）
```

- 求解在子线程跑，主线程 drain 中间解 → 经 WebSocket 推前端
- 前端收到后：① 实时渲染最新排料图 SVG ② 收敛曲线追加点 ③ 全量帧存数组（供回放）

## 七、分阶段实现

### 阶段 A：过程可视化 MVP（想法 1，先做）

| 步骤 | 内容 | 复用 |
|---|---|---|
| **A1** `solver.py` | 把 `solve_with_progress` 改造成 `solve_with_callback(instance, config, on_report)`：回调拿到完整中间解（不再丢弃 placed_items）。提供同步/异步两种用法 | `_clean_polygon`、`_transform_polygon` |
| **A2** `server.py` | FastAPI：WebSocket 端点收参数（码号 / time / seed）→ 启动子线程求解 → drain 时经 WebSocket 推中间解 JSON | `solve_with_callback` |
| **A3** 前端渲染 | WebSocket 连接 → 实时渲染排料图 SVG（`_transform_polygon` 移植 JS ≈5 行；`PTYPE_COLORS` 搬过来）+ 收敛曲线 + 帧存储 | `PTYPE_COLORS` |
| **A4** 回放 | 滑动条拖动 → 取对应 index 的帧 → 重渲染排料图 | — |

**可验证产出**：浏览器开 `http://127.0.0.1:8000`，默认「全 8 码 128 片 + 60s + seed0」点开始 → 实时看排料图随求解演变 + 收敛曲线爬升 + 拖滑动条回放任意时刻。

**阶段 A 落地确认（2026-08-08）**：
- 范围锁 baseline `{0,180}`（erode/旋转留给阶段 B 参数面板）。
- 码号默认多选（8 码全勾，可任意减到 7 码等）。
- 关键技术点：① 同步求解线程 → 异步事件循环用 `loop.call_soon_threadsafe + asyncio.Queue` 桥接，零额外依赖；② 渲染节流 ~10fps（rAF + 100ms 闸）但 `frames[]` 全量存（回放不丢帧）；③ polygon DOM 建一次、每帧只改 `points`；④ viewBox 用历史最大 width 作稳定锚，用布矩形按当前帧收缩——直观看到省布过程。

## 八、关键技术点

1. **`_transform_polygon` 移植 JS**：`rad=radians(rot); c=cos,s=sin; (x*c−y*s+tx, x*s+y*c+ty)` —— 约 5 行，与 [sparrow_baseline.py:69](nesting_engine/sparrow_baseline.py#L69) 一致。
2. **推送节流**：全量求解推送频繁（实测 289+ 报告 / 15s，全量更多）。策略：前端**限频渲染**（最新解 ~10fps 重绘 SVG），但**全量帧存数组**（回放不丢帧）。
3. **排料图 SVG 性能**：128 polygon，浏览器 SVG 无压力；全量精排时靠渲染限频保证不卡。
4. **坐标系**：SVG y 轴向下、数据 y 轴向上，用 group `transform="translate(0,H) scale(1,-1)"` 翻转（与 [`_write_svg`](nesting_engine/sparrow_baseline.py#L86) 一致）。

## 九、风险与预案

| 风险 | 预案 |
|---|---|
| 中间解高频推送致前端卡 | 渲染限频（~10fps）+ 帧按 index 存储/取回 |
| 全量精排（5–10min）前端长时间等待 | 精排走后台 + 进度心跳（复用现有 30s 心跳逻辑）+ 完成通知 |
| 中间解 placed_items 与最终解语义不一致 | 已验证：中间解 placed_items 字段完整（含 rotation），与 final sol 同结构 |
| 参数构造 instance 出错（v0.3 全量参数多） | 复用已验证的 `build_pieces('erode_rot', d)`，参数化其内部常量 |
