# 状态文件保存恢复 落地方案（.msn）

> 日期：2026-09-11 · 状态：**待评审**
> 需求：版师把工作台**运行状态**（非导出结果）保存成可传递文件，他人上传后一键还原并继续作业（查看/编辑/重解/导出）。参考 ET 软件 .pla 的用途，但不模仿其闭源二进制格式。
> 本方案由 planner 子代理两轮读码设计 + 主会话整合，行号引用以 2026-09-11 工作区代码为准。后端根 = `materialSorting-server/src/materialsorting/`，前端根 = `materialSorting-web/src/`。

## 一、已定案决策记录（用户拍板）

| # | 决策点 | 定案 |
|---|---|---|
| 1 | 恢复形态 | **完整工作台恢复**：两 Tab 数据齐全，可继续编辑、重新求解、导出 |
| 2 | 原始母版 DXF | **不打包**：只存裁片轮廓+配置+结果，仅记录来源文件名备查 |
| 3 | 策略/极限运行覆盖 | **只存最终采纳的算法结果** + provenance 来源回显；中间运行状态/run_dir 产物/逐 seed 历史一律不存 |
| 4 | 保存入口 | **并入导出弹窗**：格式下拉新增「状态文件（.msn）」，不设顶栏按钮 |
| 5 | 文件格式 | 版本化 JSON（顶层 `schema_version`）+ gzip 恒开 + 扩展名 `.msn`（仅识别/关联用，恢复端也接受 `.json`） |
| 6 | 恢复会话归属 | 写入**当前 sid**（不铸新会话、不占 `MS_SESSION_MAX=4` 名额，覆盖语义同「再上传母版 commit」） |
| 7 | 本机事实源 | 恢复**不镜像写** `out/sparrow_baseline/pieces_intermediate.json`、不落盘 uploads（他人文件不污染本机工作区） |
| 8 | 撤销栈/帧历史 | **不保存**：撤销栈是相对算法基线的下标 diff，脱离基线无意义；恢复后编辑弹窗以恢复布局为基线重锚 |
| 9 | 导出表格 6 手输字段 | 不入文件（操作者本机 localStorage 属性，跨机不应泄漏他人排料师名）；保存处 tooltip 说明 |

**衍生限制（已定案：US-005 本期打通）**：不嵌 DXF ⇒ 恢复会话上重新发起策略/极限原本会 422（`strategy.py:645` 要求 `out/uploads/<doc_id>.dxf` 在盘）。因 solve 阶段本就只吃 intermediate（`pipeline.py:358`）、DXF 仅在 commit 阶段被消费一次，故新增 CLI `intermediate` 入口短路 commit（US-005，§五/§十一）——**恢复会话的策略/极限重跑不再需要母版**。WS 普通求解/编辑/polish/导出/band-prefix 本就不受影响。**已实证**：`/export` 走会话内存态 `pieces_by_id`（`routes_views.py:359/369`），求解子进程 `solve_worker` 的几何经 pickle 传参 `pieces_snapshot`、不读磁盘（`solve_worker.py:51-58`）——恢复的纯内存会话对「导出」与「重解」两条链路均等价于正常 commit 会话。

## 三、总体方案

### 3.1 三个代码事实（决定方案形态）

1. **几何真相在后端会话，前端不持有全量**。会话 state = `{doc, gate_mm, pieces, pieces_by_id}`（`runtime._build_pieces_state`），由 commit 双写的 per-doc intermediate 构建（`server.py:155-291`；doc 结构 217-253：pieces 含 pid/label/size/polygon/bbox/area_mm2/allowed_angles + net_polygon/internal_lines/notches/grain_line 五层 + label_representatives）。前端 uploadStore 只存 doc 元数据。
2. **配置与编辑结果真相在前端**。sizes/gate/time/seed/per_type/quantities/band/prefix 全部随 WS start 每次从前端下发（`routes_ws.py:200-258`），后端会话不保存；编辑结果只存在于前端 `run.lastFrame`（editStore save 原地写回，`editStore.ts:315-324`），/export 与 /api/edit-polish 都是 placed 随 body（`routes_views.py:381`、`server.py:436-535`）——后端对布局无状态。
3. **「合成一个可恢复 run」有成熟先例**。策略结果应用 `applyStrategyResult`（`NestingPage.tsx:211-272`）：runRegistry.clear + editStore.invalidate → 合成 manifest + 单帧 phase='final' → 建 RunRecord/done。恢复端照此办理。

**结论**：「后端聚合 + 前端回传 form/quantities/run」混合结构是代码层面必然。保存 = 后端出 doc 块 + 前端回传三块，后端聚合序列化；恢复 = 后端校验重建会话 + 重算 manifest，前端两 Tab + run 合成填充。（2026-09-12 起第四块 quantities_base = 整列设值基准加入回传，见 §四 块 3b。）

### 3.2 备选对比

| | 方案 A（推荐）：后端聚合端点 + 恢复期 manifest 重算 | 方案 B：前端自包含导出 |
|---|---|---|
| 几何来源 | 后端会话 doc（与 /export、edit-polish、求解同真相源） | 前端无全量几何（事实 1），需新增「取 doc」端点 → 绕回方案 A |
| manifest | 恢复时由 `build_pid_meta(doc.pieces, sizes, per_type, quantities)` 确定性重算（纯函数无 RNG，`solver.py:190-285`），文件不存第二份几何 | 需前端存 manifest，体积 ~2×，与 doc 有漂移风险 |
| 一致性 | placed 与轮廓同源校验（pid 全匹配 + 副本守恒），复用 edit-polish 语义 | 双份几何需自行对账 |

**格式子决策**：对比 ET .pla 闭源二进制——开放 JSON 可 diff、可手工救急、可跨版本迁移；gzip 后体积足够小（§四）。

## 四、状态文件 schema 草案（v1）

```jsonc
{
  "schema_version": 1,
  "app": "materialsorting",
  "saved_at": "2026-09-11T10:00:00",
  // ---- 块 1：doc（来源 = 后端会话 state['doc']，即 per-doc intermediate 原样）
  "doc": {
    "doc_id": "3f2a...",              // 仅信息性，恢复时铸新 id
    "source": "5336#老六订单14%7%围加9.dxf",
    "gate_mm": 1750.0,
    "n_pieces": 110,
    "total_area_mm2": 10512780.4,
    "pieces": [ /* 与 intermediate pieces 逐字段同构：pid/label/size/polygon/
                  bbox/area_mm2/n_verts/allowed_angles/net_polygon/internal_lines/
                  notches/grain_line */ ],
    "label_representatives": { /* RAW 坐标代表裁片（/api/ptypes 同源） */ }
  },
  // ---- 块 2：form（来源 = 前端 formStore，FormState 全量，lib/params.ts 同构）
  "form": {
    "sizes": [30,34,35], "gate": "175.00", "time": "120", "seed": "0",
    "multi_seed": false, "seed_count": "3",
    "per_type": { "g02": { "d": 2, "tol": 0 } },
    "band_enabled": false, "band_label": "",
    "prefix_enabled": false, "prefix_front": "", "prefix_back": ""
  },
  // ---- 块 3：quantities（来源 = 前端 qtyStore，{label:{sizeKey:N}} 原生形态）
  "quantities": { "g02": { "30": 2, "34": 1 } },
  // ---- 块 3b：quantities_base（2026-09-12 additive；{label:整数} 整列设值基准 =
  //      qtyStore baseValue：整列设值弹层初值 + 特例高亮基准。省键式 = 只存 ≠1
  //      的行，全 1 / 旧文件 → 整键缺席；纯 UI 基准不参与守恒/manifest，
  //      schema v1 不 bump；恢复端原样透传回传，前端 hydrateFlat 写回 baseValue）
  "quantities_base": { "g02": 2 },
  // ---- 块 4：run（来源 = 前端 bestRun()，仅 done 态才入；无 run 时整块缺席）
  "run": {
    "seed": 0,
    // 结果来源（缺省 'solve'——v1 内可省，向后兼容手改文件）
    "provenance": {
      "kind": "extreme",                       // 'solve'|'strategy_se'|'strategy_race'|'extreme'
      "config": { "time_total_s": 600 }        // strategy 族 {"minutes":20}；solve 整键省略
    },
    "final": { "density": 0.8835, "density_sparrow": 0.8612, "width_mm": 7523.0,
               "elapsed": 121.4, "n_frames": 87, "n_eroded": 12 },
    // placed = lastFrame.placed_items（已含保存的编辑；同 pid 多副本 = 数组多条，
    // 绝不 pid 去重；mirror 按 omit-when-false 只在 true 时带键 —— editStore.ts:132-139 同口径）
    "placed": [ { "id": "g02_38", "rotation": 0.0, "translation": [-1.01, 16.22] },
                { "id": "g02_38", "rotation": 180.0, "translation": [ /* 第 2 副本 */ ] } ]
  }
}
```

**manifest 不入文件**：恢复端用 `build_pid_meta(doc.pieces, sizes=form.sizes, per_type, quantities, params=web 缺省全 0)` 重算——确定性纯函数（无 RNG，`solver.py:190-285`），与策略 result 组 manifest 同一先例（`strategy.py:1068-1092`）。产物含 erode polygon + raw_polygon + d_mm + demand + 5 层（物理毛版口径，2026-09-06 全端统一），routes_ws.on_manifest 同形下发（`routes_ws.py:268-307`）。

**provenance 取数链**：`RunRecord` 增 additive 可选字段 `origin?: {kind, config?}`——WS 求解不设（undefined = 'solve'），`applyStrategyResult` 从 `StrategyResult.mode` + summary/lastStart 记入（strategy 族 `minutes`（`types/strategy.ts:47-73`）、extreme 族 `time_total_s`（:84-96）），恢复端 `applyRestorePayload` 同款写回。保存时从 `bestRun().origin` 映射；origin 缺席 → 不写 provenance 键。恢复展示位：NestingPage 结果区一行 dim 小字（`来源：极限运行(600s) · seed N`，data-testid=`run-provenance`），常驻而非 StatusLine 瞬态文案。

**体积估算（5336 标定数据实测基础）**：intermediate 单行 JSON 110 片（大件 200+ 顶点、含 net/内线/刀口）约 0.8-1.5MB；状态文件 ≈ doc + form/quantities（10-50KB）+ placed（119 条 ≈ 13KB）≈ **~1-1.6MB raw / gzip 后 ~100-250KB**。远低于 20MB 上限（`server.py:92`）。gzip 恒开，恢复端按魔数 `1f 8b` 嗅探，纯 JSON 也接受（开发期手改友好）。

**口径注记**：run.final.density 为 real 口径 `total_area/(width×gate)`（`solver.py:674-687` `_apply_density_dual` 单一换算点）；恢复展示直接用存值，编辑保存后由前端 `computeLayoutStats` 同口径重算（`editStore.ts:81-102`，物理毛版 raw 口径包络）。

## 五、后端改动点

### 新模块 `web/statefile.py`（纯逻辑 + 路由注册，strategy.py 同模式）

1. **常量**：`STATE_SCHEMA_VERSION = 1`、`STATE_MAX_BYTES = 20MB`（对齐 `server.py:92`）、`STATE_EXTENSION = '.msn'`。
2. **`build_state_document(state, form, quantities, run, quantities_base=None) -> dict`**：聚合 doc 块（state['doc'] 原样）+ 前端回传四块（quantities_base 2026-09-12 additive，None 省键同 run 先例）；run 缺席/未完成则整块省略。
3. **`serialize_state(doc) -> bytes`**：`json.dumps(ensure_ascii=False)` + gzip。
4. **`parse_state_document(raw: bytes) -> dict`**（校验链，全 fail-fast 400，复用 edit-polish 语义 `server.py:436-535`）：
   - 魔数嗅探 gzip → 解压；解压后 > STATE_MAX_BYTES → 413；
   - `json.loads`（RecursionError/DecodeError → 400「状态文件损坏」）；
   - `schema_version`：缺失/非 int/大于本程序版本 → 400「状态文件版本过新（vN，本程序支持至 v1）」（老读新 = 明确报错不猜测；新读老 = v1 内未知顶层键忽略、可选块缺席容忍，破坏性变更才 bump 并写 `migrate_v1_to_v2`）；
   - doc 块：pieces 非空、逐片 pid/label/size/polygon(≥3 顶点且逐点数值有限)/bbox/area_mm2 形态校验、gate_mm>0；
   - run 块：placed 逐条形态（id:str / rotation:number / translation:[x,y] / mirror?:true）→ pid 全部命中 doc.pieces_by_id（否则 400「状态文件内部不一致：placed 引用母版外裁片」）→ 重算 manifest 后**副本守恒终检** `Counter(item.id) == {pid: demand}`；provenance.kind 不在枚举 → 400（config 形态宽松，纯展示不承重）。
5. **`POST /api/state-save`**：`_resolve_session_state`（`routes_views.py:39-48` 同款，default 回退）→ 读 JSON body `{form, quantities, run?}` → **保存期守恒校验**（run 存在时：placed pid 全命中会话 pieces + `Counter(placed) == demand(form.sizes × quantities)`，违者 400「数量矩阵/尺码选择与当前结果不一致，请先重新求解或改回数量再保存」——防止产出他人无法恢复的内部不一致文件，与恢复期终检同一校验函数）→ build + serialize → 文件名 `<source 去 .dxf>_状态_<yyyymmdd-HHMMSS>.msn`，Content-Disposition 中文/ASCII 双写（`routes_views.py:443-455` /export 同法）。会话过期 401 先行。
6. **`POST /api/state-restore`**：multipart 收文件（扩展名 .msn/.json，>20MB 413）→ `run_in_threadpool(parse_state_document)` → `registry.resolve(sid, create=True)`（commit 先例 `server.py:294-384`）→ **纯内存重建 state**：`state_from_doc(doc)`（自 `runtime._build_pieces_state` 提取的 dict 直建变体；doc_id 铸新 uuid，源文件名保留在 doc.source）——sid 会话 `st.state = 新 dict`、default 走等价原子重绑（不镜像写 INTERMEDIATE、不落盘 uploads）→ manifest 重算 + parse 载荷组装（复用 `parse_payload._build_parse_payload`）→ `edit_hold.refresh(sid)` → 响应。
7. **`register_statefile_routes(app)`**：server.py 文件尾注册（`strategy.py:1126-1139` 同模式）。

### 既有文件

- `web/runtime.py`：提取 `_state_from_doc(doc_dict)`（现 `_build_pieces_state` 的路径读取与 dict 构建解耦，二者共享后者）。
- **US-005 相关（策略/极限重跑打通）**：
  - `cli/config.py`：`TOP_LEVEL_KEYS` 增第 10 键 `intermediate`（str 路径，与 `master_dxf` **二选一**——都给/都不给 → ConfigError；路径解析同 master_dxf 双候选口径）；

## 七、会话与多会话交互

- **恢复写入当前 sid**：apiFetch 保证 ms_sid 存在；`resolve(create=True)` 与 commit 同语义；不额外消耗名额；会覆盖当前 sid 的 doc（与「再上传一个母版 commit」同语义，前端可在有未保存工作时弹确认——v1 仅确认弹窗，不做合并）。
- **TTL/钉住**：恢复后会话即普通会话（600s 空闲逐出 → 墓碑）；编辑弹窗内 `lib/editHold.ts` 4min 心跳照常续命；求解中 ws_acquire 钉住——既有机制零改动。
- **恢复响应载荷**（复用组合）：`{doc_id, filename, parse: <_build_parse_payload 产物>, manifest: <build_pid_meta 重算>, final, placed, form, quantities}`。相比「新统一载荷」，复用组合让 PreviewPage/NestSVG/run 合成三处消费方零解析改动；代价是响应内几何三份（~2-3MB，本机/局域部署可接受，文件本身仍单份几何）。
- **默认会话**：restore 走内存原子重绑，不写盘（与 commit 的双写有意分歧：commit 镜像服务于 CLI 管线事实源，restore 不应静默替换本机默认工作区数据）。
- **策略/极限结果面板恢复语义 = 不重建**（硬证据）：status/result 是 run_dir 产物的**无状态读**（`types/strategy.ts:15-17`：产物文件 + pid 推导，刷新即恢复进度；`strategyStore.ts:10-18` refresh 只采纳本族 mode、**idle 恒采纳 = 恢复出口**）。恢复会话没有 run_dir，伪造 `phase:'done'` 塞进 store 后任何一次 `refresh()` 都会拿回 idle 打回去——伪造态天然不稳定，此路架构上死路。**定论**：恢复为主画布 done 结果态 + `run-provenance` 来源小字；两个策略/极限弹窗回 idle 配置态，可立即发起新 run（经 US-005 intermediate 入口，无需母版即可重跑）。run_dir 服务器路径本就不上屏（`StrategyRunModal.tsx:33-34`），零冲突。

## 九、边界与风险清单

| # | 边界/风险 | 处置 |
|---|---|---|
| 1 | 大文件/恶意 JSON | 20MB 上限（413）；gzip 后限额；深嵌套 RecursionError 捕获为 400；解析入 threadpool |
| 2 | 求解中保存 | run 块仅取 done 态 bestRun，否则整块省略；经导出入口的保存被既有 exporting/solving disabled 双保险天然拦截（`ExportButtons.tsx:55`），无新增竞态面 |
| 3 | 恢复后母版再变更（新 commit） | placed/export pid 失配走既有 400（edit-polish、`routes_views.py:393-395`）；runRegistry 随重解 clear |
| 4 | 状态文件被手改导致 placed 与 doc 不一致 | 恢复端 pid 全匹配 + 副本守恒双校验 400 |
| 5 | 并发保存 | 请求级无状态生成字节流，无冲突；同会话并发 restore 以后到者为准（同 commit 语义） |
| 6 | 编辑撤销栈不保留 | 定案：下标寻址 diff 脱离原基线无意义；恢复后 open 重锚基线 = 恢复布局 |
| 7 | 导出表格手输字段不随文件走 | 有意（操作者本机属性）；保存说明行文案注明 |
| 8 | 恢复会话上策略/极限重发起 | US-005 本期打通（CLI `intermediate` 入口 + commit 短路 + strategy start 分支落 doc 到 run_dir），无需母版；WS 重解/编辑/导出本就不受影响；provenance 仅展示 |
| 9 | manifest 重算跨版本微差 | 仅影响 erode 灰虚线参考线；raw_polygon/物理口径/导出不受影响；schema_version 门控大改 |
| 10 | 多副本不变量 | placed 同 pid N 条数组项；save 深拷贝原序、restore 原序回填、守恒终检三道锁 |
| 11 | 「纯配置档」UI 不可达 | 导出按钮需 lastFrame；端点层仍容忍无 run——契约与 UI 能力差写进 agent-api-reference 防误用 |
| 12 | provenance 系展示级冗余 | 可被手改，恢复端只验枚举不验真伪；来源行失真不影响任何计算/导出；结果经人工编辑后来源仍标原始运行（如「极限运行」），属可接受的表述粒度 |
| 13 | 改数量/码选后未重解即保存 | A 产出内部不一致文件（placed ≠ 新 demand）→ B 恢复期终检 400。**保存期同款守恒校验 fail-fast**（§五.5），A 当场得到明确报错，不让坏文件流出到他人手上 |
| 14 | .msn 链式传递（A 恢复→改→存→B 恢复→…） | 文件自包含（doc+form+quantities+run），恢复 = 内存重建会话（等价一次 commit）、doc_id 每次铸新，无 lineage/原文件依赖，链路无限传递；策略/极限 422 限制沿链继承 |
